## Requirements, storage, optimizations and remedies

All estimates below are engineering planning budgets, not benchmark measurements. A RAM upgrade is conditional on the actual laptop's serviceability; no slot/upgradeability claim is made. Freeing RAM is a user action; this task did not stop applications, Docker or services.

### Surya 2

CPU minimum software: supported Python >=3.10 plus a compatible llama-server; native Windows llama.cpp CPU builds exist but this Surya integration is untested here. GPU vLLM needs Linux/WSL and its pinned engine's supported compute capability (current guide: >=7.5), beyond MX350 6.1. The 650M weight file is 1,372,368,672 bytes from official repository metadata; full environment/artifacts may need about 10 GiB disk (estimate). No llama-server presence or quantized checkpoint was certified. Lower concurrency/context and a verified compatible GGUF/quantization may reduce memory, with changed precision explicitly recorded; no variant conversion occurs automatically. More RAM may make CPU trials viable; driver/toolkit changes cannot fix GPU architecture. Optional cloud profile below resolves GPU/RAM constraints. [Release setup](https://github.com/datalab-to/surya/blob/v0.22.1/README.md), [llama.cpp Windows CPU builds](https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md), [current vLLM platform requirements](https://docs.vllm.ai/en/latest/getting_started/installation/gpu/).

### PaddleOCR-VL 1.6

Official requirements for GPU Paddle/Transformers: CC >=7.0 and CUDA >=11.8; accelerated vLLM route CC >=8.0/CUDA >=12.6. MX350 misses the architecture requirement even though the driver advertises newer CUDA. CPU is officially available; current RAM fails the planning budget. Native Windows CPU avoids a required container, whereas accelerated servers need the documented container/Linux arrangement. Main model file is 1,917,255,968 bytes; layout assets and environment are additional. Reserve roughly 12 GiB disk and 16-32 GiB host RAM (estimates); caches/container duplication may exceed this disk budget. Reduce batching, concurrency and resolution only under explicit recorded settings. Quantized/remote/alternative backend use requires separate approval and validation. Recommended cloud A10G/L4 profile below supplies adequate modern architecture. [Official hardware/backend matrix](https://www.paddleocr.ai/main/en/version3.x/pipeline_usage/PaddleOCR-VL.html), [model artifacts](https://huggingface.co/PaddlePaddle/PaddleOCR-VL-1.6).

### Marker 2

Current Marker uses Surya's inference server for scanned-page OCR; CPU is possible, but 8 GB total RAM cannot meet our conservative 10+ GiB process planning budget. This is a budget-based restriction, not an invented documented hard minimum. Recommended 24-32 GiB host RAM, 12 GiB disk for environment and assets (estimates); shared Surya weights do not establish total Marker footprint. Native CPU path is conditional on tested server integration; GPU serving uses Linux/WSL with a modern supported GPU. Use one worker, single-page jobs and declared mode; disable external LLM enhancement. Skipping OCR is not an equivalent optimization. A higher-RAM CPU host or the common cloud GPU configuration is the viable option. [Marker release](https://github.com/datalab-to/marker/blob/v2.0.0/README.md), [dependency metadata](https://pypi.org/pypi/marker-pdf/json).

### Standard PaddleOCR

A free Windows x64 CPU trial is plausible once at least roughly 2 GiB process headroom plus OS reserve is available; no CPU inference latency has been measured. Reserve roughly 2 GiB additional environment/model storage, more for cached wheel duplication (estimate). Exact download sizes depend on the approved English and Arabic detector/recognizer pair; no model-family total was verified. Do not install GPU Paddle beside CPU Paddle. Smaller approved detector/recognizer variants, disabled optional orientation/unwarping modules, batch 1 and bounded page resolution can control resources but alter the declared configuration. No WSL/Docker/GPU is required for CPU. Prefer freeing RAM/8-16 GiB host before any cloud option; a 4-vCPU/16-GiB CPU host is an optional paid fallback. [Official language-model selection](https://github.com/PaddlePaddle/PaddleOCR/blob/v3.7.0/paddleocr/_pipelines/ocr.py), [CPU platform deployment](https://www.paddleocr.ai/main/en/version3.x/pipeline_usage/OCR.html).

### Tesseract

Official tessdata_fast tree metadata lists eng 4,113,088 bytes and ara 1,432,056 bytes; these are individual language files, not a full install estimate. Reserve roughly 0.25 GiB if only adding data/output overhead, excluding datasets (estimate). Use one page at a time, thread cap, fixed DPI and a declared fast/best language family; resolution/data-family changes affect accuracy. No CUDA, WSL or Docker needed; CPU speed and layout limitations remain unmeasured. Free RAM first; an optional 2-4-vCPU/8-GiB CPU host is sufficient as a conservative starting configuration, but cloud costs are unnecessary for this candidate.
